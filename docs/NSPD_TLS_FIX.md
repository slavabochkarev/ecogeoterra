# Исправление защищённого подключения НСПД

13 ноября 2026 года, Europe/Samara. Проект `C:\Project\ecoburo-geo`.

## Результат

Защищённое соединение восстановлено без отключения проверки сертификатов. Поиск номера `63:09:0102159:753` и отдельный POST по полному контуру OSM `way/135674075` вернули HTTP 200. Пространственно найден один кандидат — **земельный участок**, а не кадастровая запись здания. Реальные характеристики отображены в интерфейсе. `pynspd==1.1.15` сохранён, новые зависимости не устанавливались, другие функции приложения не менялись, EXE не собирался.

## Точная причина

Запросы направляются на **`https://nspd.gov.ru`**, SNI и проверяемый hostname — **`nspd.gov.ru`**. URL не подменяется IP-адресом, перенаправления не следуются:

- `GET https://nspd.gov.ru/api/geoportal/v2/search/geoportal?query=63%3A09%3A0102159%3A753&thematicSearchId=1`
- `POST https://nspd.gov.ru/api/geoportal/v1/intersects?typeIntersect=fullObject`

Сервер передаёт три сертификата, включая промежуточный и корневой. Цепочка полная, но **Russian Trusted Root CA отсутствовал среди доверенных корней**: в Windows ROOT/CA, в `ssl.create_default_context()` и в certifi. Наличие самоподписанного корня в присланной цепочке не даёт ему доверия.

Точное исключение Python с системным SSL-контекстом:

```text
SSLCertVerificationError
[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate in certificate chain (_ssl.c:1010)
verify_code: 19
verify_message: self-signed certificate in certificate chain
```

Windows `curl.exe` использует **Schannel**. С обычной системной проверкой тот же endpoint также отклонён: exit code **60**, **`SEC_E_UNTRUSTED_ROOT (0x80090325)`**. HTTP-запрос в этом случае не был отправлен, поскольку TLS не установился. Это не случай, когда Windows доверяет, а Python не может построить цепочку.

`truststore` рассмотрен: он предоставляет доступ к системному доверию Windows, но не может создать доверие к отсутствующему корню. Поэтому новая зависимость не добавлялась. Python уже импортировал доверенные сертификаты Windows в свой контекст (75 X.509, 71 CA; в Windows ROOT — 68 записей, CA — 27), но нужного отпечатка среди них нет. HTTPX получает явно созданный SSLContext; certifi не является хранилищем этого контекста.

`SSL_CERT_FILE`, `SSL_CERT_DIR`, `REQUESTS_CA_BUNDLE`, `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NSPD_CA_FILE` на момент диагностики **не установлены**. В отчёте записаны только признаки наличия переменных, без их значений и прокси-учётных данных. У адаптера `trust_env=False`, автоматические HTTP-прокси и `PYNSPD_*` не используются. У OpenSSL отсутствуют файловые CA по стандартным путям, однако `ssl.create_default_context()` на Windows загружает сертификаты из системных хранилищ.

Подключение без дополнительного CA по-прежнему корректно отклоняется и после исправления: хранилища Windows не изменялись. Успешно устанавливается только контекст адаптера с проверенным дополнительным корнем.

## Исправление и происхождение CA

Корень независимо скачан из официального источника — [CDN портала Госуслуг](https://gu-st.ru/content/Other/doc/russian_trusted_root_ca.cer), по HTTPS с `verify=True`, без прокси и без отключения hostname. Получен HTTP 200, 2088 байт. Домен `gu-st.ru` указан в ресурсах официальной [страницы Госуслуг](https://www.gosuslugi.ru/crt). Сертификат загружен напрямую, проверки/защитные страницы портала не обходились.

DER SHA-256 официального файла совпал с корнем серверной цепочки. После независимого получения доверенного корня выполнены `openssl verify` для цепочки с `-purpose sslserver -verify_hostname nspd.gov.ru` и реальный проверяемый TLS-handshake. Сертификат из непроверенного handshake не использовался как источник доверия. Для наблюдения цепочки `openssl s_client` запускался с **`-verify_return_error`**: соединение обрывается при ошибке, принятия недоверенного сервера нет.

Файл включён в исходники как `app/certs/russian_trusted_root_ca.pem`, происхождение описано в [app/certs/README.md](../app/certs/README.md). При создании контекста:

1. Создаётся стандартный системный `ssl.create_default_context()`.
2. Проверяется закреплённый DER SHA-256 встроенного файла.
3. Этот CA добавляется через `load_verify_locations(cadata=...)` только в контекст НСПД.
4. HTTPX использует именно этот контекст: **`verify_mode=CERT_REQUIRED`**, **`check_hostname=True`**.

Несовпадение отпечатка, повреждённый/отсутствующий CA, неподтверждённая цепочка или неверное имя приводят к ошибке. Небезопасного fallback нет. Глобальное хранилище Windows, certifi и другие клиенты не изменяются. Автоматической загрузки CA при старте нет. Явный `NSPD_CA_FILE` остаётся доступен и заменяет встроенный дополнительный CA, сохраняя системное доверие.

Во время первого GET после TLS-исправления обнаружена ошибка старого разбора: `meta` — массив записей по категориям, а адаптер ожидал словарь. Формат подтверждён также сохранённым исследовательским ответом. Исправлена проверка массива и полноты по `totalCount`, добавлены два теста. Для подтверждения исправления сделан **один дополнительный GET**; пространственный POST не повторялся. Итого после исправления TLS — **два GET по одному номеру и один POST по одному контуру**, без сканирования территории.

Протоколы:

- Первый GET/POST после исправления TLS вернул два HTTP 200. Пространственный результат получен без кеша. Первый GET отклонён старым разбором `meta`.
- При повторном GET номер успешно разобран, пространственные данные прочитаны из кеша. Сырые ответы и диагностика среды сохранены локально.

Интерфейс отобразил поля площади, статуса, категории, адреса, ВРИ и кадастровой стоимости найденного участка.

Для браузерной проверки использован отдельный временный стенд с сохранённым реальным OSM-ответом, явно обозначенным в строке состояния. Сам адаптер и API НСПД не подменялись. Кнопка получила **реальный пространственный результат из кеша**, записанного защищённым POST, поэтому новый запрос НСПД для снимка не потребовался. Стенд остановлен; обычное приложение доступно на порту 8001. Фиктивные кадастровые данные в этой проверке не использовались.

## Повторный запуск

Перезапустите старый процесс сервера и обновите страницу браузера. Для обычного запуска `NSPD_CA_FILE` не нужен:

```powershell
cd C:\Project\ecoburo-geo
powershell -ExecutionPolicy Bypass -File .\start.ps1 -Port 8001
```

Откройте [ЭкоГеоТерра](http://127.0.0.1:8001), выберите объект и нажмите «Получить кадастровые сведения». Если старые процессы занимают порт, завершите их обычным способом или выберите другой свободный порт.

Автономные проверки:

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
.\.venv\Scripts\python.exe -m pip check
```

Ограниченная сетевая проверка (каждый запуск делает новые обращения НСПД):

```powershell
.\.venv\Scripts\python.exe scripts\check_nspd.py --osm-feature C:\GeoData\control.geojson --output .cache\nspd-check.json --cache-dir .cache\NSPD
```

Диагностика цепочки использует установленный OpenSSL из Git и системный curl, не устанавливает дополнительное ПО:

```powershell
.\.venv\Scripts\python.exe scripts\diagnose_nspd_tls.py
```

Успех подтверждён для одного номера и одного полигона. Живой WMS в точке, полнота выдачи на других территориях и получение ОКС этим примером не подтверждены. При официальной смене корня его нужно повторно получить из проверенного официального источника и обновить отпечаток; простое принятие нового сертификата от сервера недопустимо. Старая EXE-сборка не обновлялась и исправления не содержит.
